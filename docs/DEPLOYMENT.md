# Внедряване, защита и архиви

## Подготовка на сървър

Използвайте Linux сървър с Docker, постоянен диск и собствен HTTPS адрес. Копирайте хранилището, създайте `.env` с `python scripts/init_local.py` и настройте:

- `ALLOWED_HOSTS=реалният-домейн` — без протокол и без `*`.
- `CSRF_TRUSTED_ORIGINS=https://реалният-домейн`.
- `HTTPS=1`; при доверен reverse proxy пред loopback web порта: `TRUST_PROXY=1`.
- Постоянни, частни `DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD` и `TOKEN_ENCRYPTION_KEY`. Локалният генератор създава независими случайни стойности.
- Реалния Google OAuth клиент и одобреното уведомление, ако ще използвате Google Forms.

Стартирайте `docker compose up -d --build`, после `docker compose exec web python manage.py createsuperuser`. Публикувайте само reverse proxy порта за HTTPS. Web и PostgreSQL портовете в Compose са обвързани с 127.0.0.1. Не публикувайте `runtime/private`, `.env`, `runtime/pgdata` или архивите като статични файлове.

Reverse proxy трябва да подава `Host` и `X-Forwarded-Proto` от доверения TLS terminator. Настройката `TRUST_PROXY` се включва само зад такъв proxy. За отдалечена PostgreSQL база задайте собствен `DATABASE_URL` с проверено TLS свързване и подходящи сертификати. Директната PostgreSQL връзка в предоставената Docker мрежа е вътрешна.

Преди въвеждане в експлоатация изпълнете миграциите, тестовете и `python manage.py check --deploy` с действителните production настройки. Проверете достъпа с профили администратор, счетоводител и само преглед. Задайте счетоводно потвърдените правила и периоди; инсталацията не ги активира автоматично.

Няма създаден общ администратор с фабрична парола. Системният профил за проверката на примерните документи е с неизползваема парола и се деактивира след проверката.

## Архивиране

От хост машината, в корена на проекта:

```bash
python scripts/backup.py
```

Получава се частен архив в `runtime/backups` с PostgreSQL custom-format dump, оригиналите, частните файлове и manifest с контролна сума. Той съдържа лични и финансови данни и евентуални **шифровани** OAuth разрешения — пазете го защитено и копирайте извън сървъра според университетската политика. Самият `.env` и ключовете не са включени. Пазете отделен защитен архив на конфигурацията и ключовете, особено `TOKEN_ENCRYPTION_KEY`.

Планирайте периодично изпълнение, срок за съхранение и проверка на възстановяването. Архивите на същия диск не са достатъчна защита срещу загуба на сървъра. При мащабна активна работа използвайте резервни копия и на ниво дискова снимка/управляван PostgreSQL и съгласувана политика за файловете.

## Възстановяване

Първо възстановете в **нова временна база** и проверете контролната сума и броя източници/записи. Не презаписвайте действаща база без архив и планиран прозорец за поддръжка.

```bash
docker compose exec -T db createdb -U pfplus pfplus_restore_check
docker compose exec -T db pg_restore --exit-on-error -U pfplus -d pfplus_restore_check < /защитен-път/database.dump
docker compose exec -T db psql -U pfplus -d pfplus_restore_check -c 'SELECT count(*) FROM ledger_sourcedocument;'
```

След успешна проверка спрете web услугата, възстановете избраната продукционна база по административната Ви процедура, възстановете частните файлове в `runtime/private`, оригиналите и оригиналната защитена конфигурация. При вече попълнена целева база `pg_restore` изисква отделно планиране на премахване/замяна на съществуващите обекти; примерът по-горе е за празна нова база. След това изпълнете миграциите и повторете функционалната проверка.

Подготвената облачна среда държи PostgreSQL данните в bind mount под `/workspace`, за да не разчита на жив процес или на съществуването на Docker named volume в следваща машина. Съхранявайте и проверен dump преди публикация. Публикуването на облачната среда и публичното внедряване на приложението са различни операции.

## Организационни настройки

Университетът определя правните основания, сроковете за съхранение, правата на служителите и процедурата за искания по лични данни. Ограничаването на показването на контактите в приложението не е автоматично заличаване на счетоводна история. Уточнете тези правила преди работа с реални регистрации.

Генерираните документи са проекти за административно утвърждаване. Не заменят официалната счетоводна система, счетоводното потвърждение на ставките, банковата сверка или подписването.
